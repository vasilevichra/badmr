# Табло 110 — перенос наработок табло Новой лиги: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Перенести на табло 110 визуальные и поведенческие наработки табло Новой лиги: маркеры чётности кортов и подающего, назначение подачи и коррекция чётности судьёй, серверный движок чётности/подачи, корректные оси свайпов на повёрнутом телефоне.

Серверный движок — порт логики НЛ из `src/repositories/game.ts` (свойства чётности/подачи при каждом очке), адаптированный под ростер пар по разрядам (`teamOrderService.avatars()` + индекс текущего разряда `game_type_pos`, который клиент отправляет при смене разряда). Клиент — маркеры и жесты в `lib.js`/`board.ejs` по образцам из `game.js` (НЛ), с гардами по префиксу id модалок 110.

**Tech Stack:** TypeScript (node:sqlite, Express), jQuery + Bootstrap-модалки, node:test + node:sqlite тестовый стенд (`tests/helpers/migration.ts`).

**Spec:** `docs/superpowers/specs/2026-11-14-board-110-nl-design.md`

## Global Constraints

- Все правки SQL — в существующие миграции (`migrations/01-tables-up.sql`), новых .sql-файлов не создавать.
- Репозитории/роуты принимают `tournamentId?: number` с фолбэком на global current (схема `requestedTournament`); новые роуты принимают `?tournament=` через `requestedTournament(req)`.
- Проверка тестов: `rm .data/test.stamp && npm run test` (покрытие не должно упасть ниже ~95.5%).
- Русский язык в комментариях/тестах; стиль существующего кода (табличные SQL-строки, комментарии «зачем», а не «что»).
- Деплой не входит в план (выполняется пользователем явно).
- Список разрядов и порядок строк табло: `['МО', 'ЖО', 'МП', 'ЖП', 'СП']`, два круга через разделитель «•»; `game_type_pos` — индекс 0..9 текущей строки (0 = МО первого круга), состав разряда одинаков в обоих кругах.
- Парные разряды: МП, ЖП, СП (у команды двое на корте); одиночные: МО, ЖО.

**Логика increase (порт НЛ `game.ts:112–209`, адаптация):**

1. Матч нет/finished → null (как сейчас).
2. Ростер: `players1 = groupPlayers(teamId1, g.game_type_pos)`, `players2 = groupPlayers(teamId2, g.game_type_pos)`. `even = {1: g.even_1_user_id ?? players1[0], 2: g.even_2_user_id ?? players2[0]}`; если stored even не входит в текущий ростер (деградация/смена разряда без type-pos) — фолбэк на `players[0]`.
3. `servingTeam` — по `g.serve_user_id`: какой из ростеров содержит его; null — подача не задана.
4. Инкремент счёта (как сейчас), затем — если очко выиграла подающая команда и в её ростере двое — её `even` становится напарник. `serve_user_id` = игрок пары-победителя: чётный счёт пары → её even, нечётный → напарник; в одиночке (ростер из 1) сервер всегда сам игрок. Подача не задана — считаем очко выигранным на приёме: без смены кортов, сервер вычисляется по чётности счёта пары-победителя (как в НЛ).
5. Далее существующая логика кратности 11 (автозачёт, finished на 110) — без изменений.
6. Ростер пуст (0 игроков разряда) — счёт инкрементируется, even/serve не трогаются.

- Produces (сигнатуры репозитория; сервис — те же имена с `= (...) => this.game110....(...)`):

```

setCurrentServeByTeamIds(teamId1: number, teamId2: number, userId: number, tournamentId?: number): Promise<Board110State | null>
setTypePosByTeamIds(teamId1: number, teamId2: number, typePos: number, tournamentId?: number): Promise<Board110State | null>
```

**Правила (из спеки):**

- **decrease**: инкремент-зеркало. Граница: если убавляемый счёт кратен 11 до декремента — even/serve не трогать (семантика «убавление не отменяет сыгранную партию»). Иначе эвристика НЛ (`game.ts:217–262`): убавили счёт подающей пары → откат смены кортов + подающий по чётности нового счёта; убавили счёт принимающей → подача возвращается бывшей подающей паре, корты не менялись, подающий по чётности её счёта. Счёт не изменился (был 0) — even/serve не откатываются, вернуть состояние.
- **swap**: граница партии `(score_1 % 11 === 0) XOR (score_2 % 11 === 0)` или оба 0; иначе null. Игра отсутствует — создать (create при отсутствии не нужен: swap имеет смысл только при открытой игре; вернуть null, если игры нет). `even_X` → напарник из ростера (ростер из 1 игрока — вернуть состояние без изменений). Если подаёт свапаемая пара — подающий на корт по чётности её счёта.
- **serve**: только оба счёта 0; только игрок из ростера одной из команд; только чётному игроку пары (`even_X`; в одиночке — единственному). Игра отсутствует — создать строку `game_110` (create c `game_type_pos = 0`). Возвращает состояние.
- **type-pos**: только на границе (та же XOR-логика; 0:0 — разрешён, т.к. восстановление после перезагрузки шлёт pos 0); иначе null. Сохраняет `game_type_pos`; пересчитывает `even_X` по наследованию половин: если старый `even_X` был вторым игроком старой группы — новый even = второй игрок новой группы (иначе первый); старый even вне старого ростера — база (первый). Пересчитывает `serve_user_id`: победитель прошлой партии — сторона, чей счёт кратен 11 (при 0:0 подача не трогается — остаётся как была, т.е. NULL или тап судьи); подающий — игрок пары победителя: чётный счёт → even, нечётный → напарник (одиночка — сам).
