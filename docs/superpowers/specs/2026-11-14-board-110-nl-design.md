# Табло 110: перенос наработок табло Новой лиги

Дата: 2026-11-14 · Статус: на утверждении

## Зачем

Визуальная часть живого табло Новой лиги (НЛ) отточена: маркеры чётности
кортов и подающего, жесты судьи по игрокам, корректные оси свайпов на
повёрнутом экране телефона. Табло 110 (марафон) этими наработками не
пользуется. Задача — перенести их в 110 с учётом правил турнира.

## Цели / не-цели

**Цели:**
- палочки чётности и воланчик подающего на табло 110;
- назначение подачи судьёй на 0:0 (тап/двойной клик);
- ручная коррекция чётности свайпом/кликом в начале каждой партии;
- автоподача и авточётность по ходу игры (сервер);
- оси свайпов с учётом CSS-поворота на телефоне (как в НЛ).

**Не-цели:**
- не трогаем существующую логику счёта 110 (кратность 11, автозачёт 5×n,
  салют, плашки таймаута/смены сторон) — она уже отточена;
- не переносим механику НЛ «половинный свап решающей игры» — в 110 её нет;
- таблица `game` (НЛ) не меняется.

## Правила 110 (подтверждены пользователем)

1. Палочки чётности — только в парных разрядах (МП/ЖП/СП). В одиночных
   (МО/ЖО) — только воланчик подающего.
2. Пары **не** обмениваются кортами между партиями: игроки следующего
   разряда команды начинают с той же половины, что и предыдущие.
3. Подающая команда следующей партии — победитель предыдущей; подаёт её
   игрок с корта, соответствующего чётности счёта команды (чётный счёт —
   чётный/правый корт).
4. Подача выставляется судьёй только на 0:0 матча (первая партия); дальше
   — автоматически по счёту и чётности.
5. По ходу игры действует движок НЛ: пара, выигравшая очко на своей
   подаче, меняется кортами; подающий — игрок пары на корте по чётности
   её счёта. Проигравшая розыгрыш пара корты не меняет.
6. Судья может править начальные положения свайпом только в начале
   партии (счёт на границе кратного 11, очков новой партии ещё нет),
   дальше — автоматика.

## Дизайн

### БД (правки в существующие миграции)

`CREATE TABLE game_110` (01-tables-up.sql) дополнить колонками:

- `even_1_user_id INTEGER` — игрок пары команды 1 текущего разряда на
  чётном (правом) корте; NULL — база (первый из группы);
- `even_2_user_id INTEGER` — то же для команды 2;
- `serve_user_id INTEGER` — подающий (NULL — не задана, до тапа на 0:0).

В `01-tables-down.sql` ничего (DROP TABLE покрывает).

### Сервер (`src/repositories/game110.ts`, роуты `src/routes/game.ts`)

Порт движка НЛ из `game.ts`, адаптация под team_1_id/team_2_id:

- **increase** (после инкремента счёта, до/вместе с существующей
  обработкой кратности 11): если очко выиграла подающая пара — её
  `even_X_user_id` становится напарник; `serve_user_id` = игрок
  пары-победителя на корте по чётности её нового счёта. Подача не
  задана (первый розыгрыш до тапа) — считаем очко выигранным на приёме:
  без смены кортов, сервер вычисляется по чётности (как в НЛ).
  Уменьшаемые кейсы одиночных разрядов: `even_X_user_id` у одиночной
  команды = её единственный игрок текущего разряда (напарника нет —
  смена кортов не происходит), маркеры не рисуются.
- **decrease**: эвристика НЛ — уменьшение счёта подающей пары = очко
  выиграно на своей подаче (откат смены кортов + подающий по чётности
  нового счёта); иначе очко на приёме (подача возвращается бывшей
  подающей паре без смены кортов). Исключение — уменьшаемый счёт стоит
  на границе партии (кратен 11): чётность и подачу не трогаем — это
  соответствует текущей семантике 110 «убавление не отменяет сыгранную
  партию» (откатываемое очко разыгрывали игроки уже закрытого разряда).
- **setCurrentServeByTeamIds(team_1_id, team_2_id, user_id)**: только
  при счёте 0:0; только чётному игроку; игру при отсутствии создаёт
  (база чётности: первые из групп — даже это решает клиент, см. ниже).
- **swapCurrentEvenByTeamIds(team_1_id, team_2_id, team_number)**:
  только на границе партии — `(score_1 % 11 === 0) XOR
  (score_2 % 11 === 0)`, либо оба 0. Оба счёта кратны 11 одновременно
  (не-нулевой случай, напр. 11:11) — не граница, отказ. Свап меняет
  `even_X_user_id` на напарника; если подаёт эта пара — подающий
  переезжает на корт по чётности счёта (как в НЛ).
- **Ответ increase/decrease/swap/serve** — состояние
  `{score_1, score_2, even_1_user_id, even_2_user_id, serve_user_id}`
  для обновления маркеров клиентом (сейчас increase ответ игнорирует).
- Новые роуты: `POST /api/games/current110/serve`,
  `POST /api/games/current110/swap`. Все принимают `?tournament=`
  (requestedTournament).

**Ростер пары на сервере:** сервер вычисляет игроков текущего разряда
через `teamOrderService.avatars(team_id)` + текущий разряд. Текущий
разряд серверу неизвестен (клиентский сдвиг списка) → добавляем колонку
`game_type_pos INTEGER NOT NULL DEFAULT 0` в `game_110` (индекс строки
текущего разряда в списке табло: 0..9, «•» не нумеруется; 0 = МО первого
круга). `increase`/`serve`/`swap` вычисляют группы из `avatars()` и
берут пару/одиночку по индексу. Клиент при `advanceBoardGameType`
отправляет новый индекс (`POST /api/games/current110/type-pos`) —
сервер пересчитывает:

- `even_X_user_id` по правилу наследования половины: первые игроки
  новых групп встают на те же половины, где стояла команда (старый
  `even_X_user_id` → чётная/нечётная половина → первый игрок новой
  группы на ту же половину);
- `serve_user_id` по правилу 3: подаёт победитель прошлой партии
  (сервер выводит его из счёта — единственная сторона, чей счёт кратен
  11; при 0:0 подачи нет), игрок на корте по чётности счёта команды.

`increase` на границе партии подачу и чётность не пересчитывает
(только счёт и автозачёт) — стык оформляет `type-pos`. Порядок
гарантируется клиентом: type-pos отправляется из колбэка ответа
increase (ответ содержит полное состояние); сервер отказывает type-pos,
когда счёт не на границе (защита от повторов и гонок).

### Клиент (`lib.js`, `board.ejs`, `index.css`)

- **board.ejs**: `.board-player` получает `data-user-id="<%= player.id %>"`;
  маркеры (палочки/воланчик) рендерит JS — разметка как в НЛ
  (`board-parity`, `board-serve` внутри `.board-player-avatar`).
- **Перестановка игроков в группе**: как в НЛ — чётный игрок пары
  рендерится первым (DOM-порядок в группе меняется вместе с маркерами),
  «правый корт» — в той же визуальной логике, что у НЛ-табло
  (общие классы и CSS-поворот).
- **lib.js**: центральная `renderBoardMarkers(modal)` — расставляет
  палочки (только парные группы МП/ЖП/СП) и воланчик по состоянию
  (полученному с сервера при открытии табло и в ответах очков/свалов).
  Состояние на матч-пару: `Map` по id модалки, как в НЛ.
  Вызовы: открытие модалки, после каждого increase/decrease (из ответа
  сервера), после swap/serve, после `advanceBoardGameType` (сброс на
  базу + отправка type-pos из колбэка increase-ответа).
- **Неполная пара** (сеяние/фолбэк `avatars()` вернул одного игрока в
  парном разряде): трактуется как одиночка — even = единственный игрок,
  свапов нет, палочки не рисуются, движок не падает.
- **Жесты**: перенос из game.js с поправкой на модалки 110
  (`[id^="tournament-groups-board-"]`): тап/двойной клик по чётному
  игроку — подача (только 0:0), клик с задержкой 250мс/свайп к напарнику
  — свап чётности (только граница партии). Команда пары определяется по
  `data-team-number` счёта своей колонки (переезжает при смене сторон).
- **Оси свайпов счёта**: `addScoreBoardHandlers` (lib.js) дополнить
  логикой НЛ — на `body.phone` в портрете рабочая ось `dx` со знаком
  вправо (контент повёрнут), в ландшафте `dy`; поперечный жест ≥30px
  гасит синтетический click. Текущий код использует только `dy`.
- **Плашки смены сторон/таймаута**: `cloneBoardPlayers` клонирует
  `.board-player` целиком — маркеры приедут сами; перед показом плашки
  вызывать `renderBoardMarkers` для свежего состояния.
- **CSS**: стили `.board-parity`, `.board-serve` уже есть в index.css
  для НЛ — селекторы расширить на модалки 110; мобильные правила
  `body.phone` для табло 110 дополнить размерами маркеров (как у НЛ).

## Мои решения (можно поправить при чтении)

1. Индекс разряда хранится в `game_110.game_type_pos` и обновляется
   клиентом отдельным лёгким POST из колбэка ответа increase (порядок
   гарантирован; сервер отказывает type-pos вне границы партии).
   Альтернатива (сервер сам выводит разряд из счёта) хрупка:
   автозачёт и корректировки судьи ломают вывод «сколько партий
   сыграно».
2. Чётность одиночных разрядов хранится (even_X = единственный игрок),
   но маркеры в одиночных не рисуются; смена кортов в одиночке
   не происходит. Это упрощает наследование половин между партиями.
3. Свап чётности судьёй разрешён при `(score_1 % 11 === 0) XOR
   (score_2 % 11 === 0)` или 0:0 — это точная граница партии; кейс
   11:11 (середина партии) отсекается.
4. `advanceBoardGameType` шлёт type-pos только при смене разряда на
   табло; открытие модалки после перезагрузки страницы восстанавливает
   состояние из `GET /api/games/current110` (там уже лежит и type-pos).
5. Уменьшение счёта на границе партии не трогает чётность/подачу
   (семантика 110 «убавление не отменяет сыгранную партию» уже
   задокументирована в коде decrease).
6. Игроки пары в группе переставляются по чётности, как в НЛ
   (визуальная часть переносится один-в-один).
7. Идущие на момент деплоя матчи: маркеры/подача могут показываться
   неверно до следующего стыка партий (type-pos = 0 при счёте не в
   начале) — деградация принимается: деплой выполняется вручную вне
   игровой сессии, прод-база пересоздаётся из дампа. Бэкфилл
   невозможен — исторический разряд серверу неизвестен.
