# Личный выбор турнира по ссылке (/tournament/:id)

## Intent и why

Сейчас приложением управляет глобальное состояние «текущий турнир»
(`tournament.current`, один на всех; переключается админом через
`POST /tournament/current/:id`). Роут `GET /tournament/:id` уже рендерит
страницу нужного турнира (шапка, достижения — серверно), но ajax-разделы
(«Игроки», «Подбор», «Корты», настройки) догружают данные по глобальному
текущему турниру. Ссылка вида `http://host/tournament/3` показывает
шапку турнира 3 и живые разделы другого турнира.

**Цель:** каждый открывший ссылку `/tournament/:id` видит все разделы
по турниру `:id`, не меняя глобальный текущий турнир для остальных.
Мотивация — «поделился ссылкой в чате, все открыли, каждый увидел свой
просмотр».

## Goals

- Ссылка `/tournament/:id` полностью отображает турнир `:id` во всех
  read-разделах главной страницы.
- Выбор турнира — персональный (в сессии), глобальный `current` не меняется.
- `GET /` ведёт на сессионный турнир, если он выбран, иначе на глобальный.
- Админское переключение турнира (`POST /tournament/current/:id`)
  обновляет и сессию (синхронизирует личный выбор с действием админа).

## Non-goals

- Параллельная работа с двумя турнирами в разных вкладках одного браузера —
  сессия одна, последний открытый турнир побеждает.
- Пер-турнирные мутации: запись игр, регистрация, платежи, корты остаются
  операциями над глобальным текущим турниром. Просмотр чужого (не текущего)
  турнира — read-only.

## Anti-goals (что было бы провалом)

- Изменение глобального `tournament.current` при переходе по ссылке.
- Поломка существующего поведения без ссылки: страница текущего турнира
  должна работать как раньше.

## Constraints

- Репозитории — синглтоны, одно SQLite-соединение на все запросы:
  per-connection состояние (TEMP-таблицы) непригодно для разведения сессий.
- Вьюхи `ready`, `players`, `archived`, `settings`
  (migrations/02-views-up.sql) жёстко фильтруют `t.current = 1`;
  SQLite-вьюхи не параметризуются.
- `WHERE t.current = 1` зашит в SQL репозиториев: court, game110, group,
  match, match110, settings, team-color, tournament, user, common.
- express-session уже подключён (SQLite store, saveUninitialized: false).
- Тесты: серверный код — TDD; публичные js/css — без тестов (node --check).

## Решённые части (как решено)

1. **Хранение выбора** — `req.session.tournamentId` (число или undefined).
2. **Установка выбора** — `GET /tournament/:id` (валидный существующий
   турнир) пишет `req.session.tournamentId = id`.
3. **Разрешение турнира** — порядок: явный параметр запроса
   `?tournament=<id>` → `session.tournamentId` → глобальный current.
   Валидация: параметр должен быть числом и существующим турниром,
   иначе fallback по цепочке.
4. **View-слой БД** — вьюхи `players`, `ready`, `archived`, `settings`
   перестают фильтровать по `t.current = 1` и отдают `tournament_id`
   (для settings — строки по каждому турниру с его override'ами);
   фильтр переезжает на место запроса: `WHERE tournament_id = ?`,
   а вызовы, работавшие с глобальным current, подставляют
   `(SELECT id FROM tournament WHERE current = 1)`. Семантика старых
   вызовов сохраняется.
5. **Репозитории** — read-методы, используемые разделами страницы,
   получают опциональный `tournamentId`; отсутствие параметра = старое
   поведение (глобальный current). Мутации не меняются.
6. **Фронтенд** — id турнира сервер рендерит в `data-tournament` на body
   (в index.ejs есть `tournament_id`); клиентский хелпер в lib.js
   добавляет `?tournament=<id>` к read-запросам разделов
   (`/api/users/`, `/api/courts/`, `/ready/`, `/api/settings/`,
   `/api/tournaments/played/`, `/api/tournaments/registered/count` и др.).
7. **Серверная защита** — mutation-эндпоинты отклоняют запрос с
   `?tournament=`, указывающим не на глобальный current (409), чтобы
   write-действия из «чужого» турнира не задели данные.
8. **Админский переключатель** — после `setCurrent(id)` сессия тоже
   получает `tournamentId = id`.

## Что осталось билдеру

- Точная инвентаризация read-эндпоинтов разделов страницы и их SQL
  (какие используют вьюхи, какие — прямые `t.current = 1`).
- **Все SQL-правки — в существующие миграции** (решение автора):
  вьюхи — правкой `02-views-up.sql` (+ down), данных — `05-specific-up.sql`.
  Отдельных 07-файлов не создавать. Prod-БД пересоздаётся существующим
  dev/migrate-циклом автора.
- Тесты: TDD на разрешение tournamentId (роут-тесты с фейковой сессией),
  тесты репозиториев с параметром (fixture: два турнира, разные данные),
  проверка сохранения старого поведения без параметра.
- Проверить страницу 404 (несуществующий турнир) и поведение анонима.

## Решения по итогам builder-check (решения билдера, помечены)

1. **View `settings` не параметризуется** (билдер): триггеры 04 читают её
   скалярными подзапросами `(SELECT value FROM settings WHERE name='wins')` —
   перевод вьюхи на строки-по-турниру тихо ломает расчёт рейтинга и
   автофиниш. Триггеры не трогаем; репозиторий settings параметризуется
   инлайн-SQL (он и так не читает вьюху).
2. **Шапка и История персонализируются** (следует из запроса автора):
   `stats()` (медианы `match.ts:227–290`) и `getAllFinishedAtLastSession`
   (`match.ts:144`) переходят на id просматриваемого турнира.
3. **CTE `cal` в `players`** — калибровочные override'ы по просматриваемому
   турниру (билдер): просматриваешь турнир 3 — видишь его калибровку.
4. **Мутации** (билдер): остаются операциями над глобальным current;
   клиент не добавляет `?tournament=` к write-запросам. Серверный 409-guard
   остаётся как defense-in-depth на случай явного параметра в write-запросе.
   `archiveAll`/`unarchiveAll` после снятия фильтра во вьюхе `players`
   получают явный `WHERE tournament_id = (SELECT id FROM tournament
   WHERE current = 1)`.
5. **Анонимные сессии** (билдер): создание cookie/сессии каждому анониму,
   открывшему ссылку, — приемлемая цена; store уже SQLite.
6. Известная протечка текущей вьюхи `settings` (возможны 2 строки на имя
   при нескольких турнирах с override) фиксится в новой версии вьюхи —
   коррелированный подзапрос по `s.tournament_id` вместо LEFT JOIN без фильтра.
