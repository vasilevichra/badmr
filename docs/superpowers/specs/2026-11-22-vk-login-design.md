# Дизайн: вход через VK (привязка к существующему аккаунту)

Дата: 2026-11-22. Статус: черновик, согласован с заказчиком в диалоге,
прошёл builder-check.

## Зачем

Игроки клуба входят по почте/телефону и паролю. Добавляем вход через VK как
альтернативный способ для уже существующих аккаунтов — меньше трения на
телефоне, где набирать пароль неудобно. Одновременно закладываем каркас,
в который позже ляжет Sign in with Apple (заказчик: Apple — на будущее).

## Решения заказчика

- VK привязывается **только к существующему аккаунту**. Регистрации через
  VK нет: если привязки нет — вход отклоняется с подсказкой привязать вручную.
- Ручной ввод vk-ссылки в карточке игрока **убирается**, вместо него —
  статус привязки и кнопки «Привязать/Отвязать».
- **Автопривязка** при входе: если VK вернул подтверждённые email или
  телефон, и в базе ровно один `user` с таким контактом — привязываем
  автоматически и пускаем внутрь (заказчик подтвердил; риск неверных
  данных в базе озвучен и принят — клуб закрытый, данные ведёт админ).
- Apple сейчас не делаем; схема должна расширяться на второго провайдера
  без переделки.

## Цели / не-цели / анти-цели

- Цели: привязка VK из карточки игрока; вход по кнопке «Войти через VK»
  на auth-страницах; автопривязка по email/телефону; отвязка.
- Не-цели: регистрация новых аккаунтов через VK; доступ к VK API
  (стена, друзья и т.п.); Apple в первой итерации; подтверждение email в базе.
- Анти-цели: чтобы «Войти через VK» мог создать дубликат аккаунта или
  отдать чужой аккаунт при неоднозначном совпадении.

## Состояние проекта (что уже есть)

- `user.vk_id` — TEXT UNIQUE, колонка уже добавлена миграцией `01-tables-up.sql`;
  `tg_id` рядом, email/phone — существующие колонки (обе UNIQUE).
- Авторизация: passport local, сессии express-session на SQLite, CSRF csurf
  (глобальный), механизм flash-сообщений на auth-страницах (`sess.messages`).
- Стилистика auth-страниц: вкладки «Вход / Регистрация», соцблок GH·VK·TG.
- TS исполняется без сборки (`node --experimental-strip-types`), импорты
  с расширением `.ts`. В тестах есть паттерн подмены `globalThis.fetch`.

## Архитектура

VK ID — OAuth 2.1 + PKCE. Старые passport-стратегии под VK ID не годятся,
поэтому провайдер реализуем напрямую, без новых npm-зависимостей. Точные
адреса и формат ответов сверяются с актуальными доками VK ID при реализации
(исторически эндпоинт токена — `https://id.vk.com/oauth2/get_token`,
JWKS — `https://id.vk.com/.well-known/jwks`; на архитектуру не влияет).

- `GET /api/auth/vk` — старт (прямая ссылка с кнопки, без промежуточной
  страницы): генерируем `state`, `nonce` и PKCE `code_verifier`, кладём в
  сессию вместе с флагом намерения (`login` или `bind`), редирект на
  `https://id.vk.com/authorize` с scope `email phone`.
- `GET /api/auth/vk/callback` — обмен кода на токены, проверка `id_token`:
  подпись RS256 по JWKS VK (кэш в памяти процесса с TTL), `iss`, `aud`
  (client_id), `exp`, `nonce` из сессии, `state` из сессии. Далее запрос
  user_info для email/телефона.
- Обобщённый каркас: один модуль `src/services/oauth.ts` (state/nonce/PKCE,
  верификация id_token, JWKS-кэш) + конфиг провайдера; Apple потом
  добавляется как второй конфиг и своя пара роутов, `apple_id` — колонкой
  в той же миграции.

### Логика callback

Порядок проверок фиксированный:

1. Подпись/срок/`state`/`nonce` провалились → сообщение об ошибке на
   странице входа через существующий механизм `sess.messages`.
2. Намерение `bind` (залогиненный пользователь привязывает):
   - если в сессии нет `req.user` (сессия истекла) — трактуем как `login`;
   - если у пользователя уже есть `vk_id` — отказ «VK уже привязан»
     (перезапись не делаем, idempotent-принцип);
   - иначе `UPDATE user SET vk_id = ?`; конфликт UNIQUE (этот VK уже у
     другого аккаунта) ловим заранее проверкой и показываем человеческое
     сообщение, не сырой 500.
3. Намерение `login`: ищем `user` по `vk_id`:
   - найден → `req.login` тем же механизмом, что у passport local
     (serializeUser хранит `{id, username}` — совместимо);
   - не найден → автопривязка по контактам VK (см. ниже); успех — логин;
   - неудача → сообщение: «этот VK не привязан: войдите почтой и
     привяжите в карточке игрока».

### Правила автопривязки по контактам

- Кандидатов ищем по email **и/или** телефону независимо; email сравниваем
  в lower-case, телефон приводим к формату схемы (`+79XXXXXXXXX`) —
  VK может вернуть отформатированный номер.
- Совпадение ровно у одного пользователя (по одному контакту) — привязываем.
- Email указывает на одного пользователя, телефон на другого (разные
  строки) — **отказ**: неоднозначно, показываем ручную привязку
  (подтверждено заказчиком).
- Совпадений нет или VK не вернул ни email, ни телефон (телефонный скоуп
  у VK ID проходит модерацию — вход считаем рабочим и без него) — отказ
  с подсказкой ручной привязки.

### Конфиг и секреты

- `VK_CLIENT_ID`, `VK_CLIENT_SECRET` — переменные окружения / локальный
  файл вне репозитория (в коде и fixtures секретов нет).
- Redirect URI (регистрируется в приложении VK, фиксируем до регистрации):
  `https://badmr.ru/api/auth/vk/callback` — роутер auth смонтирован на
  `/api/auth`; dev-адрес добавит заказчик в приложении VK отдельно.
- Cookie сессии — SameSite Lax (по умолчанию), top-level GET-редирект от
  VK проходит; запись state/verifier в сессию делает её сохраняемой при
  `saveUninitialized: false`. CSRF на callback не нужен (GET), на
  `POST /auth/vk/unbind` действует глобальный csurf, форма шлёт токен
  как остальные.

### UI

- Страница входа (и модальная ветка signup): под кнопкой «Войти» — кнопка
  «Войти через VK» (нейтральный фон в существующем стиле).
- Карточка игрока (`modal/player/id.ejs`): строка VK — если привязан,
  «привязан» + «Отвязать», иначе кнопка «Привязать VK». Управление —
  у любого залогиненного пользователя, как у остальных редактируемых
  полей карточки (ролей в системе нет). Ручной ввод vk и роут
  `POST /api/users/vk/:id` с `setVk` удаляются, покрывающие их тесты
  правятся вместе с ними.
- Отвязка: `POST /api/auth/vk/unbind` — сброс `vk_id` в NULL (idempotent).

### Electron

Подтверждено заказчиком: логин происходит в окне приложения (вью загружает
сайт) — OAuth-редирект остаётся внутри той же сессии, куки сохраняются,
отдельной работы не требуется.
